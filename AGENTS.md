# AGENTS.md

## 1. О проекте

Персональное портфолио frontend-разработчика.

Это одностраничное приложение на React и TypeScript, публикуемое через GitHub Pages.

Основная задача — представить реальные коммерческие проекты, показать личный вклад разработчика, используемые технологии и контактную информацию.

Визуальное направление: Editorial / Minimal, тёмная тема, сдержанные голубые акценты.

Портфолио полностью двуязычное: русский и английский.

Основной акцент интерфейса — проекты. Отдельный Hero-раздел не используется.

## 2. Общие правила работы

- Перед началом работы изучать этот файл и существующую структуру проекта.
- Соблюдать согласованные архитектуру, дизайн-систему и технологический стек.
- Не менять утверждённые требования без согласования.
- Не добавлять зависимости, абстракции и архитектурные слои без практической необходимости.
- Не создавать пустые каталоги, файлы и модули на будущее.
- Не усложнять небольшие компоненты искусственным разделением.
- Не привязывать переиспользуемые компоненты к конкретным проектам или их идентификаторам.
- Не дублировать состояние и данные в разных частях приложения.
- Не придумывать профессиональный опыт, обязанности, достижения, технологии и личный вклад.
- Не использовать стоковые или сгенерированные изображения вместо реальных скриншотов проектов.
- При обнаружении технического ограничения объяснять проблему и предлагать решение, а не молча менять требования.

## 3. Технологический стек

Обязательные технологии:

- Vite
- React
- TypeScript 7.x
- Tailwind CSS
- shadcn/ui
- Zustand
- i18next
- react-i18next

Не использовать:

- React Router.
- CMS.
- Внешний API для получения контента.
- Дополнительные библиотеки без обоснованной необходимости.

### TypeScript 7.x

TypeScript 7.x обязателен.

До начала реализации:

1. Проверить актуальную стабильную версию TypeScript 7.x.
2. Проверить совместимость с выбранными версиями Vite, React, Tailwind CSS, shadcn/ui и остальных инструментов.
3. Проверить совместимость средств проверки типов.
4. Не заменять TypeScript 7 на TypeScript 5 или 6 без согласования.
5. Если обнаружена несовместимость, выяснить её причину, предложить варианты решения и сообщить о проблеме.

Успешная сборка Vite не является подтверждением корректности типов.

Необходимо настроить отдельную проверку TypeScript. Использовать `tsc --noEmit`, если выбранный toolchain поддерживает этот сценарий. Если нет — предложить совместимый способ проверки, не подменяя версию TypeScript.

Проверка типов и production build должны выполняться отдельно и успешно завершаться.

## 4. Архитектура

Использовать feature-oriented структуру с разделением ответственности.

Предлагаемая структура:

```text
src/
  app/
  components/
  features/
    projects/
    about/
    contact/
    navigation/
  content/
    types.ts
    projects.ts
    site.ts
  assets/
    images/
      nsign/
      harbour-space/
      seafood-shop/
      interlabs/
  store/
  i18n/
    locales/
      ru/
      en/
  hooks/
  lib/
  styles/
  App.tsx
  main.tsx

public/
  .nojekyll

scripts/
  optimize-images.ts

docs/
```

Структуру разрешается адаптировать под реальную реализацию. Не создавать файлы и каталоги, которые не используются.

Назначение:

- `app/` — инициализация приложения, корневая композиция и провайдеры.
- `features/` — секции страницы и их логика.
- `components/` — общие компоненты и адаптации shadcn/ui.
- `content/` — типизированные данные и конфигурация содержимого.
- `assets/images/` — оригинальные скриншоты проектов.
- `store/` — общее UI-состояние.
- `i18n/` — настройка локализации и переводы.
- `hooks/` — действительно переиспользуемые хуки.
- `lib/` — общие утилиты.
- `styles/` — глобальные стили, шрифты и дизайн-токены.
- `scripts/` — скрипты сборки, в том числе оптимизация изображений.
- `docs/` — результат production build для GitHub Pages.

Архитектура должна оставаться пропорциональной размеру приложения.

## 5. Источник данных и управление содержимым

Приложение должно быть data-driven.

Содержимое страницы не должно быть зашито непосредственно в React-компоненты.

Репозиторий является единственным источником контента. Не использовать CMS, базу данных или внешний сервис.

### Проекты

Использовать единый типизированный массив проектов:

- `src/content/types.ts` — интерфейсы и типы.
- `src/content/projects.ts` — массив проектов.
- `src/i18n/locales/ru/projects.json` — русские тексты проектов.
- `src/i18n/locales/en/projects.json` — английские тексты проектов.

Структура проекта должна поддерживать:

- Стабильный идентификатор.
- Порядковый номер.
- Название.
- Компанию.
- Период.
- Ключ перевода роли.
- Ключ краткого описания.
- Ключ подробного описания.
- Ключ описания личного вклада.
- Список технологий.
- Ссылку на публичный сайт.
- Обложку.
- Галерею изображений.

Пример контракта:

```ts
export interface Project {
  id: string;
  number: string;
  title: string;
  company?: string;
  period?: string;
  roleKey: string;
  shortDescriptionKey: string;
  descriptionKey: string;
  contributionKey: string;
  technologies: string[];
  website?: string;
  cover: string;
  gallery: string[];
}
```

При необходимости интерфейс можно уточнять, но разделение метаданных и локализованных текстов должно сохраняться.

### Требования к данным

- Карточки, боковая панель, галерея и навигация должны использовать один массив проектов.
- Порядок Previous / Next определяется порядком элементов массива.
- Добавление нового проекта не должно требовать изменения React-компонентов.
- В компонентах запрещены условия, привязанные к конкретным ID проектов, если для этого нет реальной функциональной причины.
- Не дублировать сведения о проекте в разных источниках.
- Ссылки на изображения должны быть понятными и предсказуемыми.
- По возможности проверять наличие переводов и файлов изображений.
- Отсутствующие необязательные данные должны корректно обрабатываться интерфейсом.

Добавление проекта должно сводиться к:
1. Добавлению объекта в `projects.ts`.
2. Добавлению переводов в RU и EN.
3. Добавлению изображений в каталог соответствующего проекта.

### Остальное содержимое страницы

По тому же принципу централизовать повторяющиеся и редактируемые данные:

- Контактные ссылки.
- Основную информацию о разработчике.
- Название специализации и стек.
- Другие повторно используемые значения.

Для этого можно использовать `src/content/site.ts` и соответствующие файлы локализации.

Не создавать универсальную CMS-подобную систему. Достаточно типизированных объектов и массивов.

## 8. Framer Motion и анимации

Использовать Framer Motion (`framer-motion`) для анимаций интерфейса.

Подходящие сценарии:

- Появление секций при прокрутке.
- Появление карточек проектов в области видимости.
- Fade-in / fade-out.
- Hover-анимации.
- Переходы между состояниями интерфейса.
- Анимации боковой панели там, где они дополняют поведение shadcn Sheet.
- Небольшие переходы интерактивных элементов.

Преимущественно использовать `opacity` и `transform`.

Не анимировать каждый элемент и не перегружать интерфейс движением.

Учитывать `prefers-reduced-motion`.

Не дублировать одну и ту же анимацию одновременно через CSS и Framer Motion без необходимости.

Не использовать тяжёлые 3D-сцены, custom cursor и глобальный parallax.

Отдельный Hero Flow не нужен.

## 9. Появление карточек и ленивая загрузка

Карточки проектов должны появляться постепенно при прокрутке страницы.

Использовать Framer Motion `whileInView` или эквивалентный viewport-механизм.

Требования:

- Плавное появление с использованием opacity и небольшого transform.
- Однократное срабатывание при первом появлении карточки в области видимости, если это уместно.
- Без тяжёлых последовательных анимаций всей страницы.
- Не задерживать получение и отображение самих данных проектов.
- Не использовать сложную виртуализацию для семи карточек.

Для изображений использовать нативную ленивую загрузку там, где это уместно.

Анимация появления карточек и загрузка изображения — разные механизмы. Не смешивать их состояния.

## 10. Zustand

На старте использовать один небольшой Zustand store.

Состояние:

- `activeProjectId`
- `isProjectSheetOpen`

Действия:

- `openProject(id)`
- `closeProject()`
- `navigateProject(direction)`

Не хранить в Zustand:

- Индекс активного изображения галереи.
- Текущий язык.
- Локальное состояние отдельных компонентов.

За активный слайд отвечает Embla. За язык — i18next с сохранением выбора в localStorage.

Избегать дублирования состояния между React, Zustand и i18next.

## 11. Локализация

Использовать i18next и react-i18next.

- Весь пользовательский интерфейс должен иметь RU и EN версии.
- Использовать `useTranslation()` и `t()`.
- Организовать переводы по секциям и доменам содержимого.
- Тексты проектов хранить в переводах.
- Метаданные проектов хранить отдельно от переводов.
- Сохранять выбранный язык в localStorage.
- Переключение языка не должно требовать перезагрузки страницы.

Локализовать также состояния ошибок, доступные подписи и элементы управления.

## 12. Изображения и Sharp

Оригинальные скриншоты хранить в:

`src/assets/images/`

Каталоги группировать по проектам.

При сборке использовать Sharp для генерации AVIF.

Результаты сохранять в:

`public/images/`

Скрипт оптимизации должен:

- Сканировать каталоги оригинальных изображений.
- Сохранять структуру каталогов проектов.
- Конвертировать поддерживаемые форматы в AVIF.
- Сохранять исходные размеры и пропорции.
- Не изменять оригинальные файлы.
- Не создавать дубликаты и устаревшие файлы.
- Давать понятные сообщения об ошибках.
- Обеспечивать воспроизводимый результат при повторной сборке.
- Не допускать излишней потери качества, особенно на скриншотах с мелким текстом.

Генерируемые AVIF-файлы не редактируются вручную.

Учитывать Vite `base` при формировании путей к изображениям.

### AppImage

Создать общий компонент `AppImage`, используемый в карточках и галереях.

Компонент должен поддерживать:

1. Loading — skeleton или ненавязчивый preloader.
2. Loaded — отображение изображения.
3. Error — нейтральная заглушка при ошибке загрузки.

Дополнительные требования:

- Lazy loading там, где он нужен.
- Сохранение размеров и пропорций до загрузки.
- Отсутствие скачков сетки при загрузке.
- Сброс состояния при изменении источника.
- Отсутствие бесконечного skeleton при ошибке.

Не создавать отдельные реализации загрузки изображений для карточек и галереи без необходимости.
